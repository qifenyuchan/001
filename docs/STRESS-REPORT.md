# 压力测试报告 — northstar-memory 2.15.0

> 目标：同一台机器上的真实服务（stdio MCP / HTTP MCP / UI 共用一份数据目录）
> 时间：2026-10-22　平台：Windows / 8 核 / Node 22.22 / NVMe
> 压测台：`npm run stress`（`stress/run.mjs`，14 组用例，结果 `stress/report.json`）
> 回归：`tests/stress.test.mjs`（4 条，已进 `npm test`）

## 一、结论先说

1. **读路径原本跟会话数成正比，跟记录数无关**——每次读写都给每个会话 `stat` 一次 `.rev`。
   200 个会话时 `get` 要 18.37ms、`save` 要 83ms。改成空间级 rev 快路径后：
   **`get` 18.37ms → 0.50ms（36×）、`save` 83.25ms → 35.82ms（2.3×）**。
2. **连带抓到一个「一有脏目录就整库重扫」的 bug**：会话目录名不合规时加载器不登记状态，
   `目录数 === 会话数` 永远不成立 → 每次操作都全量重载。已修。
3. **剩下的墙是检索**：3000 条 p50 34.6ms / p95 57.7ms，单次检索会**阻塞整个进程 123ms**，
   8 并发时 p50 涨到 401ms。这是「无索引 + 单线程同步」的必然结果，不是 bug。
   文档里 Q5 索引的触发条件是「总量过 5000 或用户抱怨」——**现在 3000 条，未触发**。
4. **写吞吐的天花板是 fsync，不是 CPU**：全规模下都是 27–34ms/条（≈30 条/s），
   与记录数无关；600 轮的单会话也没变慢（32.0 → 33.7ms）。
5. **没有泄漏**：20s 混合负载 5292 次操作 0 错误，GC 后 heap 35.5 → 25.0MB（下降）。

## 二、规模曲线（修复后）

| 记录数 | 冷启动 `open()` | 写 p50 | recall p50 | search p50 / p95 | list p95 | RSS | heap |
|---|---|---|---|---|---|---|---|
| 200 | 0.44s | 31.8ms | 0.59ms | 4.5 / 19.5ms | 1.3ms | 59MB | 11MB |
| 1 000 | 1.14s | 32.8ms | 0.57ms | 11.3 / 20.2ms | 6.4ms | 83MB | 25MB |
| 3 000 | 2.97s | 32.4ms | 0.35ms | 34.6 / 57.7ms | 1.0ms | 97MB | 37MB |

- 40 个会话、每级增量灌数据，读写各 30–50 次取分位；RSS 含压测进程本身（HTTP 服务、undici 连接池）。
- `search` 随记录数线性增长（200→3000 涨 7.6 倍），因为语料要全量展开打分，没有索引。
- `recall` 与 `list` 几乎不受规模影响——它们只碰内存里的 Map。

## 三、会话数敏感性（本轮核心发现）

同样 **200 条记录**，只是切分方式不同：

| | 200 个会话 × 1 轮 | 8 个会话 × 25 轮 | 倍数 |
|---|---|---|---|
| `get` p50（修复前） | 18.37ms | 1.22ms | **15.1×** |
| `save` p50（修复前） | 83.25ms | 28.32ms | 2.9× |
| `list` p50（修复前） | 18.6ms | 0.73ms | 25× |
| `get` p50（修复后） | **0.50ms** | 0.36ms | 1.4× |
| `save` p50（修复后） | **35.82ms** | 30.78ms | 1.2× |

**根因**：`maybeRefresh()` 为了做跨进程失效判断，遍历 `this.sessions` 逐个 `revStamp(dir)`
（一次 `statSync`）。Windows 上单次 `stat` 约 75µs，200 个会话就是 **15ms**——而这个检查
压在**每一次**读写上。会话越多越慢，跟记了多少东西完全无关。

**修法**（保持语义，不是关掉检查）：

- 写入时同时推进**空间级** `.rev`（`data/spaces/<space>/.rev`），
  于是「有没有别人写过」只需 **1 次 stat**；
- 目录数仍比对（增删会话能立刻发现）；
- 逐会话的深检**限流到 1 秒一次**，用来兜住「外部工具直接往会话目录里丢文件」这种没经过本进程写入的情况。

**语义变化（写清楚，别当没发生）**：经本进程或另一个 RepoStore 写入的数据，**立刻可见**（走空间 rev）；
外部硬盘/同步盘直接落盘的文件，最迟 **1 秒**内可见（深检窗口）。原来的实现也是靠 `.rev` 的 mtime
判断，同样看不见「不动 `.rev` 的外部改动」，所以这不是新增的盲区，只是把检查频率降了。

**连带 bug**：`loadSession` 遇到目录名不合规（含空格/点号）时直接 `return`，没有登记进
`this.sessions`。于是 `dirs.length === this.sessions.size` **永远不成立**，`maybeRefresh` 每次都判定
「有变化」→ 整库重扫。放一个 `bad dir.name` 目录进去，每次读都要重扫 3000 条。
现在会登记这个空占位会话（`P-2` 用例锁住）。

## 四、并发与尾延迟：单线程的真相

| 场景 | 结果 |
|---|---|
| 10 个检索「同时」发出（`Promise.all`） | 串行 365ms / 并发 356ms，**加速比 1.03×** |
| 单次检索阻塞事件循环 | **123ms**（这期间 `/api/health`、MCP 所有请求都在排队） |
| 10 次连续检索阻塞 | 721ms |
| 单次写入阻塞 | 34ms |
| HTTP MCP，8 并发 × 12 轮（3000 条） | 19 req/s，p50 **401ms** / p95 589ms，失败 0 |
| HTTP MCP，串行 | recall 4.1ms / search 41.4ms / save 33.3ms |

加速比 1.03× 说明瓶颈是**单线程 CPU**，不是 IO 等待：所有库操作都是同步的，并发只是排队。
排队时最倒霉的那个请求要等前面所有请求的**总和**——所以 8 并发 p50 是串行的 10 倍。

这不是缺陷，是模型选择（同步文件 IO + 单进程，换来「无锁无竞态、写入永不半条」）。
真实使用里一个 Agent 是串行调用工具的，并发主要来自「UI 开着 + Agent 在跑 + 另一个 Agent 共用实例」。

## 五、跨进程：锁与数据完整性

4 个进程 × 15 轮，全部抢写**同一批 `turn_no`**（天然键冲突的最坏情况）：

- 墙钟 3.81s，**成功 60/60**，锁超时 0，其它错误 0；
- 落盘 **15 条**（不是 60 条），不同轮次 15 个 —— 天然键去重正确，revision 递增，没有出现两份。

说明 `withLock`（mkdir 原子性 + 30s 残留自愈 + 进程存活判断）在真并发下是对的。

## 六、冷启动：架构的固定代价

| 场景 | 耗时 |
|---|---|
| `open()` 3000 条 | 2.97s（≈1.0ms/条） |
| CLI `stats` / `search` / `get`（3050 条） | 3.99s / 3.96s / 3.91s |

一条记录一个 JSON 文件，启动就要把全部文件读一遍、解析一遍、重算质量分。
**常驻进程只付一次**（MCP 模式下 Agent 感觉不到），但 CLI 每次调用都付一遍——
「人在终端里查一条」在万条规模会变成 10 秒级。

这是「文件即数据、单一真源、O(1) 保存」的对价，不是能随手优化掉的。真要治只有两条路：
按会话懒加载（改动大，会破坏 `all()` 的语义）或加 sidecar 索引（就是 Q5，且要保证索引可重建）。

## 七、泄漏与稳定性

20 秒混合负载（6 并发，读为主 + 少量写）：

- 5292 次操作 / 265 op/s，**错误 0**，p50 13.6ms / p95 29.5ms / p99 70.3ms；
- `heap` 从 35.5MB **降到** 25.0MB（`--expose-gc` 后），RSS 反而涨 25MB ——
  RSS 受分配器 arena 与 GC 节奏影响，**判泄漏要看 GC 后的 heap 而不是 RSS**；
- 与修复前对比：214 op/s → 265 op/s（+24%），p99 98.7ms → 70.3ms。

## 八、SLO 对照

目标来自 `docs/QUALITY.md` §4.3（p95，1 万条）：

| 操作 | 目标 | 实测（3000 条，p95） | 判定 |
|---|---|---|---|
| `save` | < 50ms | 43.9ms（HTTP 端到端） | ✅ 余量不大 |
| `recall` | < 20ms | 4.1ms（HTTP 端到端） | ✅ |
| `search`（无索引） | — | 57.7ms | ⚠️ 有索引目标 < 50ms |
| UI `/api/list` | — | 8.1ms（800 条） | ✅ |
| UI `/api/export` | — | 27ms（800 条，全量） | ✅ |

**Q5 索引是否该做**：按文档的触发条件（总量 > 5000 或用户抱怨）——**还没到**。
但这次多了一个新证据：**8 并发时 p50 涨到 401ms**。也就是说，如果出现「多人/多 Agent 共用一个实例」，
撞墙的不是记录数，而是并发数。结论：先按「一个 Agent 一个实例」用；等真有共享实例需求，再按会话分片做索引。

## 九、本轮修了什么

| 问题 | 修法 | 收益 |
|---|---|---|
| 每次操作 O(会话数) 次 `stat` | 空间级 `.rev` 快路径（1 次 stat）+ 深检限流 1s | `get` 36×、`save` 2.3× |
| 脏目录导致永久整库重扫 | 不合格目录名也登记为空占位会话 | 消除「一个目录毁掉全部性能」 |
| （新增）压力回归 | `tests/stress.test.mjs` 4 条：会话数无关 / 脏目录 / 跨实例可见 / 外部落盘 1s 内可见 | 锁住上面两条 |

验证：`npm test` 201 → **205 全绿**；`npm run eval` 无回归（Hit@5 0.965 / MRR@5 0.928，
p50 2.68ms → 1.65ms）；`npm run attack` 仍 34/36（两条为已记录的设计取舍）。

## 十、建议（按收益/成本排序）

1. **检索文本缓存**（成本低，收益 ~18%）：`docTexts()` 每次查询都要把全部记录小写化展开，
   3000 条要 10.5ms。按 `id:revision:profile` 缓存即可，失效天然安全。
2. **按会话分片索引**（成本高，收益 5–10×）：只在总量过 5000 或需要共享实例时做，
   否则会破坏 O(1) 保存——这是 `QUALITY.md` §4.3 已论证过的结论，本轮实测没有再推翻它。
3. **冷启动**：想治只能懒加载或 sidecar；两者都会动到「单一真源」的边界，先不做。
4. **共享实例**：与其优化并发，不如规定「一个 Agent/一个人一个实例」，数据目录共享靠 rev 同步。

## 十一、本轮没覆盖的

- 机械硬盘 / 网络盘：本机 NVMe 上 fsync 27–34ms，机械盘与 SMB 会成倍放大，写吞吐会更低。
- Windows Defender 实时扫描对「一条一文件」的影响（可能是冷启动 1ms/条的一部分）。
- 小时级长稳：只跑了 20s，没做 1 小时 soak，也没做 fd 计数（Windows 无 `/proc`）。
- 多机同时写同一份云盘目录：跨进程锁只在同机文件系统上验证过，
  云盘（OneDrive/Syncthing）的锁语义不可靠，那属于「冲突副本 + 字段合并」的路径。
- 内存受限机器（< 2GB）：3000 条 heap 37MB，尚未测 OOM 边界。
