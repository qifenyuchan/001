# 如何做得更好：质量模型与提升路径

> 生成时间：2026-10-20　|　依据：当前代码（v2.6.0，零依赖，3641 行）+ 四轮调研数据
> 这份报告不问「市场要什么」（那是 `UPGRADE-PLAN.md`），只问**「什么样的记忆服务算好，现在差多少，怎么补」**。

## 0. 一句话结论

北极星现在的**骨架是对的**（单一真源、有界注入、可编辑、零依赖、安全边界扎实），
但**打磨不足**：排序没有统计权重、召回说不清为什么、检索是全量扫描、没有任何评测。
换句话说——**能站住，但还不算好用**。下面是十个维度的体检与补法。

## 1. 质量体检表

自评 1–5 分（3 = 可用，5 = 同类最好）。评分依据是代码现状，不是愿望。

| 维度 | 现状 | 目标 | 一句话诊断 |
|---|---|---|---|
| 数据完整性 / 耐久 | **4** | 5 | 原子写、锁、revision、`.trash`、墓碑都齐；缺不变量测试与损坏隔离 |
| 有界性（不撑爆上下文） | **5** | 5 | 只注入 1 条 + 字符预算 + lite 3 工具，这条是同类最强 |

## 2. 五个必须承认的短板

### 2.1 排序：现在是「命中数」，不是「相关性」

`scoreRecord` 做的是：词项在字段里出现 → 按字段权重累加，命中全词再加 5 分，加邻近加成。
**问题有两个，都是统计检索的常识：**

1. **没有 IDF**。「今天」「问题」「帮我」这类词在所有记录里都出现，命中和关键词一样算分；
2. **没有长度归一**。一条 3000 字的记录能命中更多词项，天然压过一条 30 字但精准命中的记录。

后果：搜索「部署」，一条「部署失败，因为 k8s 权限」的短记录，会输给一条流水账里顺带提了三次「部署」的长记录。

**补法（核心，不是包）**：BM25-lite——保留现有字段权重，加上 IDF 与 `1/(1+b·len/avgLen)` 长度归一。改动集中在 `core/score.ts` 一个文件，约 40 行，可先用现有语料回归对比。
数据佐证：R1 里 18 个记忆项目明确用 FTS5/BM25；R2 的混合检索共识也是「BM25 打底 + 融合」。

### 2.2 说不清「为什么召回」

现在 `search` 返回一个 `score` 数字。用户和 Agent 都无法判断这条该不该信。
R3 的 lineage 洞察（「没人告诉你凭什么」）在这里是现成的空白。

**补法**：`explain` 参数（默认关）。返回每个词项的贡献：`[{term:"部署", field:"事情", w:2.5, hit:2}]`，
以及最终分构成（词项分 + 触发加成 + 衰减系数）。UI 里折叠成「为什么这条」。
成本低（打分函数本来就知道每一项），收益是**信任**——记忆服务最贵的成本就是用户不敢信。

### 2.3 检索是全量扫描

`searchRecords` 调 `repo.all()`：把整个 `data/` 下所有记录文件解析一遍再打分。
1000 条大约几十毫秒还能忍；1 万条就是几百毫秒到秒级。而 `save` 已经优化成 O(1) 定位了，**只有检索落下了**。

**补法**：倒排索引（作为包 `recall-index`，见 PACKS.md）——`onSave/onDelete` 增量维护，
索引存 `data/.packs/recall-index/`，**可随时从真源重建**。这不破坏单一真源：
索引是派生数据，删了不影响任何记录。

### 2.4 中文：不是「不能用」，是「不精准」

**这里要修正前几轮的一个判断。** 第二/三轮报告说「中文分词是前置条件」——那是在 **FTS5** 语境下成立的（FTS5 默认分词器对中文无效）。
但当前实现走的是另一条路：`tokenize` 对 CJK 做 **bigram 切分**，`countHits` 用子串匹配。所以**中文检索是可用的**。

它的问题变成另外两个：
1. **精度**：bigram 会误配（「人工智能」与「人工」共享 bigram「人工」），且单字查询（「剑」）不产生 bigram；
2. **成本**：子串扫描 + bigram 展开，记录越多越慢。

**补法**：bigram 保留，加三件事——单字回退（1 字查询直接单字匹配）、停用词（「的/了/是」不参与打分）、索引侧用**同一套分词**（保证索引与查询一致，这是 FTS5 方案最容易踩的坑）。

### 2.5 没有评测，等于没有方向

现在能证明「测试通过」，但证明不了「召回变好了」。没有评测，任何排序改动都是凭感觉。

**补法**：见 §4.2。这是**所有质量工作的前置**——不做这个，其他改进无法验证。

## 3. 其余五维的补法（简要）

- **耐久 4→5**：补不变量测试（见 §4.1）、单文件损坏时隔离而不是整库失败、`northstar export --all` 全量备份。
- **可修正 3→5**：`northstar undo <id>` 恢复到上一版（`.trash` 已在存，缺的是命令）、编辑 diff 视图。
- **可迁移 4→5**：导出 Obsidian 兼容 Markdown vault（升级包 F）；`--export json` 全量。
- **可信 1→4**：`source` 标记（user_input / web_content / file / tool_output）、注入特征**标记不拒绝**、UI 高亮。成本低，先把字段落地。
- **可组合 2→4**：本体 + 包架构，见 `PACKS.md`。

## 4. 横切质量实践（比功能更重要）

### 4.1 不变量清单——直接写成测试

这些是「无论怎么操作都必须成立」的性质，比逐条用例更能防回归：

1. **不丢**：任意写入顺序、任意并发，已确认写入的记录必可读回；
2. **可覆盖**：同 `(session_key, turn_no)` 重复保存 = 覆盖，`revision` +1，旧版进 `.trash`；
3. **有界**：注入内容恒 ≤ 1 条上一轮 + 预算内附加段；总字符 ≤ `recall_max_chars`；
4. **单一真源**：删掉 `data/.packs/` 与任何派生文件后，全部记录仍可读；
5. **删除语义**：`purge` 必留墓碑；衰减绝不影响可读性，只影响排序；
6. **失败隔离**：任何包加载失败、索引损坏，核心仍能启动并读写；
7. **不可串会话**：跨会话召回必须显式指定，默认不越界。

建议用属性测试（property-based）方式跑随机操作序列，不需要引入依赖——手写 200 组随机序列即可。

### 4.2 评测集：已落地（55 条，可换真数据）

`eval/seed.json` 里是**合成语料**：三段不同领域的中文会话（部署事故 / 写作计划 / 家庭琐事，32 条记录）+ 55 条查询及期望命中。

```bash
npm run eval                  # 摘要 + 未命中清单
npm run eval -- --verbose     # 全部用例
npm run eval -- --min-mrr 0.85  # 低于阈值退出码 1（CI 已挂）
```

**当前基线（2026-10-20，BM25-lite 已上线）**

| 指标 | 数值 |
|---|---|
| Hit@5 | 0.982 |
| Recall@5 | 0.982 |
| MRR@5 | 0.908（旧命中计数 0.898） |
| 延迟 p50 / p95 | 1.8ms / 2.7ms（合成集）；1000 条时 9.7ms / 20.4ms |
| 注入最长块 | 86 字符（预算 1200） |

**这个数字必须打折看。** 查询是我按语料写的，天然带字面重叠——**合成集的分数系统性偏高**。
它现在的用途是**回归**（改排序后不能变差），不是证明「检索很好」。

一个诚实的失败案例：查询「部署失败」期望命中的两条记录里，**一个字面词都没有**
（一条写「连接池被打满 / 服务超时」，一条写「决定回滚」）。关键词检索在这里必输——
这正是「可选语义检索」真正该上场的地方，而不是平时。

**换成真数据的方式**：从自己的历史里抽 50 条真实提问（尤其「只记得大概内容」那种），
人工标 1–3 条期望，替换 `seed.json` 的 `queries`。合成集会一直偏乐观，真数据才会暴露真问题。

参照：`memorylens-bench`（专测记忆衰减）、`srs-benchmark`（间隔重复的评测范式）——都是「先有尺子再改进」。

### 4.3 性能预算（SLO）与实测

| 操作 | 目标（p95，1 万条） | 实测（1000 条） |
|---|---|---|
| `save` | < 50 ms | 24.8 ms/条（含落盘） |
| `recall`（注入） | < 20 ms | < 2 ms |
| `search`（无索引） | — | p50 9.7 ms / p95 20.4 ms |
| `search`（带索引） | < 50 ms | 未做，见下 |

**为什么索引（Q5）先不做——三个实测数字：**

1. 1000 条记录（平均 52 字）只有 **2107 个词项、33200 条倒排**，存成 JSON 约 **0.6 MB**；
2. 按线性外推，1 万条约 6 MB——**如果每次保存都重写整个索引文件，就把刚优化好的 O(1) 保存破坏掉了**；
3. 现在 1000 条检索 p50 9.7 ms，1 万条约 100 ms。**这是「点一次搜索等 0.1 秒」，不是「每轮都要付」**。

结论：索引要做得对，必须**按会话分片**（只重写变动的那一片），否则省下的检索时间会从保存那边还回去。
在真实规模越过 ~5000 条、或有人抱怨检索慢之前，做它属于提前优化。

**触发条件**：单会话记录数过千，或总记录数过 5000，或用户明确反馈「搜索要等一下」。

### 4.35 深度测试发现（2.11.0）

把测试从「函数级」扩到「场景级」后，抓到四个真问题——都不是靠读代码能看出来的：

| 问题 | 表现 | 修法 |
|---|---|---|
| 单字段没有长度上限 | 5 万字字段原样落盘（148KB/条），一个网页倒进「事情」就能撑爆仓库 | 硬上限 5000 字，截断并置 `truncated`，写入仍不拒绝 |
| `turn_no: 0 / -5` 被静默当成自动编号 | 调用方的错误被吞掉，记录悄悄落到下一轮 | 只在「没传」时自动编号；传了非法值报 `INVALID_ARG` |
| CLI 与 MCP 校验不一致 | MCP 拒绝空输入，CLI 却能写一条空记录 | CLI 补同样的 `EMPTY_INPUT` 守卫 |
| 方案不匹配的报错信息是死循环 | 「active profile is custom; run: profile use custom」（让人切到已经激活的方案） | 改成「请求了 general，当前是 custom，先 profile use general」 |

结论：**同一件事在两个入口（MCP / CLI）必须用同一套校验**，否则测了一个入口等于没测。

### 4.4 数据格式版本与兼容承诺

记录里已有 `schema` 字段。补一条明文承诺：**新增字段只增不改；删除字段先保留只读两版**。
升级包引入的字段必须走 profile 声明（原因见 PACKS.md §6），不能悄悄塞进 `fields`——
`normalizeFields` 会丢弃未声明的键，这既是限制也是保护。

### 4.5 发布冒烟：证明「发出去能跑」

`npm run smoke` 做一件测试之外的事——**把仓库打成 tarball，装进干净目录，再当真实用户跑一遍**：
save → search --explain → pack install（creative / export-obsidian）→ profile 切换 → 触发式注入 →
obsidian 导出 → versions / undo → stats。11 项断言全过才算发布就绪。

为什么必须有这一层：单元测试跑的是**源码树**，而用户拿到的是 `files` 清单筛过的 tarball。
漏掉 `ui/`、`packs/`、`profiles/` 任何一项，测试全绿但装完就废。这个脚本第一次跑就抓到了两个真问题
（导出命令需要另一个包；切方案后不能回写旧方案同一轮）。

CI 上只在一个 Node 版本跑（省时间），本地发布前必须跑。

### 4.6 失败降级而非失败

三层降级：包加载失败 → 跳过该包，核心继续；索引损坏 → 回退全量扫描；字段残缺 → `degraded` 记录照常展示。
**任何一层都不许让服务起不来。**

## 6. 怎么知道自己变好了

三个数字，每月看一次：

1. **eval MRR@5**：召回排序质量（上升 = 排序变好）；
2. **疑似投毒记录数**：`source=web_content` 且 `suspect` 的比例（下降或稳定 = 防线有效）；
3. **召回未引用率**：召回了但 Agent 下一轮没引用的比例（下降 = 召回变准）。

这三个数不追求漂亮，追求**可比较**。记忆服务的质量问题从来不是「差一点」，而是「没人量过」。
