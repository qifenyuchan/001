# 模拟测试报告 — northstar-memory 2.15.0

> 目标：照 `docs/AGENTS.md` 的约定，用一个「守规矩的 Agent + 几个不守规矩的 Agent」把真实服务跑一遍。
> 方式：**真进程 + 真协议**（spawn `dist/server.js`，按 stdio 逐行发 JSON-RPC），不 mock、不直接调函数。
> 时间：2026-10-22　压测台：`npm run sim`（`sim/run.mjs`，10 个场景）　回归：`tests/sim.test.mjs`

## 一、结论

**10 个场景、179 条断言全通过**。抓到 3 个真问题（全部已修，且都是「静默错」而不是「崩溃」）：

| # | 问题 | 为什么会出事 | 现在 |
|---|---|---|---|
| 1 | 锁超时在 MCP 层变成 `IO_ERROR` | `withLock` 抛的是普通 `Error`，工具层只认 `NorthstarError` | Agent 收到 `LOCK_TIMEOUT`，知道「稍后重试」而不是「磁盘坏了」 |
| 2 | 终端里 `profile use story`，常驻服务不认 | active 方案在构造时缓存，跨进程写 `profile.json` 没人看 | 切换会推进空间 rev，重扫时重读 active + 刷新方案注册表 |
| 3 | 字段被截断，`memory_save` 返回值不提 | `SaveResult` 里没有 `truncated` | 返回值带 `truncated:true`，Agent 能自己收敛内容 |

还有 1 个**已知弱项**（不修，见 §4）和 1 个**看起来像 bug 的设计**（见 §5）。

## 三、三个真问题

### 1 ｜ 锁超时被降级成 IO_ERROR（影响 Agent 的重试决策）

- 现象：`.locks/` 里有一个持有者存活的锁时，`memory_save` 返回
  `{"error":{"code":"IO_ERROR","message":"lock timeout: fault"}}`。
- 根因：`src/store/files.ts` 的 `withLock` 造了个普通 `Error` 再挂 `code` 字段；
  而 `mcp/tools.ts` 的 `fail()` 用 `e instanceof NorthstarError ? e.code : "IO_ERROR"` 判定。
- 危害：Agent 拿到 `IO_ERROR`，会当成「磁盘/权限故障」而放弃或报错给用户；
  实际语义是「另一个进程正在写，3 秒后重试就好」。这是**错误码语义被吞掉**，比抛异常更坏。
- 修复：`withLock` 改抛 `NorthstarError("LOCK_TIMEOUT")`。UI 的 503 映射与 CLI 都不受影响。
- 回归：`M-3`

### 2 ｜ 跨进程切方案不生效（错误信息自相矛盾）

- 现象：Agent 写 `profile:"story"` → 被拒，报错说
  「active profile is general … Switch first: `profile use story`」；
  用户照做，在终端跑了 `profile use story`，再写 → **还是被拒**，报同一句话。
- 根因：`active` 在 `RepoStore` 构造时读一次就缓存；`profile.json` 是另一个进程写的，没人看。
- 危害：这是「按提示操作后仍然失败，且提示内容变成谎言」——比不给提示更伤信任。
- 修复：`setActiveProfile()` 推进空间 rev（其它进程的失效检查会看到）；
  重扫分支里重读 `profile.json`，并 `profiles.refresh()`（否则新装的方案 id 认不出来）。
- 回归：`M-4`

### 3 ｜ 写入被截断，但返回值不说

- 现象：把 20KB 塞进「事情」→ 落库成功，字段被截到 5000 字并标 `truncated:true`，
  但 `memory_save` 的返回体里**没有任何字段**体现这件事。
- 危害：Agent 以为存全了，就不再做「这条太长，拆成两条」的补救；用户下次检索到的是被剪过的内容。
  这与项目自己的铁律「答错了但看起来正常，比报错更危险」是同一类。
- 修复：`SaveResult` 增 `truncated?`，三个 upsert 都回填，MCP 返回体带出。CLI 因为是展开输出，自动就有了。
- 回归：`M-2`

## 四、已知弱项（记录在案，本轮不修）

**单字主题在长口语查询里会整块丢失。** S2 的 10 次回溯里漏了 1 次：

```
查询「上次说的锁」→ 期望第 19 轮，实际前五：9,8,6,5,4
```

机制很清楚：`tokenize` 对中文只切 **bigram**（`上次/次说/说的/的锁`）并保留整段粗分词。
`锁` 这个单字不在词项里；而目标记录的「事情」写的是`把「锁」这条链路的边界说清楚`，
不含 `的锁`——于是它在这几个词项上**全部得 0 分**；反过来，那些「写入路径的锁覆盖范围」
的通用记录命中 `的锁`，把前五占满。

这不是 bug 是取舍：加 unigram 会让「的」「了」这类高频字污染排序，必须配 IDF 阈值才安全。
它与评测集里 fuzzy 类 Hit 0.571 是同一个结构性弱项（`QUALITY.md` 已记录），
要动就得连带重跑评测调参——属于「语义检索/排序」专项，不该混在模拟测试里做。

**给用户的实话**：让 Agent 检索时把主题写成词而不是单字（`锁竞争` 而不是 `锁`），命中率会明显更好。

## 五、看起来像 bug 的设计（不是 bug）

1. **坏文件占用的轮次号不回收。** 目录里有 `turn-0009.json`（半条）和 `turn-0010.json`（id 非法）时，
   下一次保存落到 **第 11 轮**，不是第 4 轮。这是刻意的：宁可留缺口，也不覆盖可能还能救回来的文件。
   代价是 `gaps` 会有假缺口，收益是「断电写了一半」不会导致后续写入把证据抹掉。
2. **每 10 轮多出一条「范围总结」。** `range_every=10` 时第 10/20/30 轮会自动生成机械范围条，
   `stats.total` 会多于轮次数。S1 里我一开始就把它当成「多出来的脏数据」判失败了——那是我的剧本错，不是服务多写。
3. **`memory_recall` 返回的是「最新一轮」，不是「写之前的那一轮」。** 所以「取 → 存」和「存 → 取」
   拿到的东西不同；协议规定的顺序是**先取后存**（`AGENTS.md` 第 1、2 条）。我第一版剧本写反了，
   30 轮全部判失败——**先把剧本校准，再相信结果**。

## 七、本轮没覆盖的

- **真实宿主**：没在 Claude Desktop / Cursor / Cline 里真接一遍（只保证协议线格式一致）。
  真宿主会带来「工具名怎么描述才被调用」「instructions 会不会被忽略」这类问题，得人工验。
- **多机同步盘**：S9 是手工放冲突副本模拟的，没跑两台机器 + OneDrive/Syncthing 的真链路。
- **UI 点击路径**：S5 走的是 MCP 工具，没模拟人点「编辑/删除/恢复」按钮（`ui-write` 测试覆盖了接口层）。
- **超长会话**：S1 只到 30 轮、S2 到 40 轮；上千轮的行为靠压力测试的 S12 兜（单会话 600 轮写入不退化）。
- **模型侧行为**：Agent 会不会真的遵守「轮首取、轮末存」无法在本地验证——这决定了记忆方案的实际成色，
  只能靠真实使用观察。
